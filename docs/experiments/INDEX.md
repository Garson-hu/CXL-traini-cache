# Experiment Index

One row per experiment, newest first. This file is the record of experiments
that is kept in the Git repository.

Everything else about an experiment stays local and is not tracked:

- `experimental_results/<experiment>/` holds its plan, summary, result tables,
  figures, and metadata.
- `$CXL_TRAINING_DATA_ROOT/results/<experiment>/` holds large raw data.

An experiment is named `YYYY-MM-DD-<short-name>`, after the day it started.
Conventions: [experimental_results/README.md](../../experimental_results/README.md).

| 2026-11-24 | `2026-11-24-large-scale-cache-evaluation` | Under a large working set and a storage-bandwidth limit, does the existing reuse-aware cache (static pinning, known order, known order with two-epoch prefetching; 256 GiB in CXL memory) deliver data to 32 to 40 jobs with less waiting than direct BeeGFS? | real hardware (cache server on c28 with the full catalog and a 278 GB store in `/dev/dax1.0`; miss path against direct reads from 20 client nodes; storage probes); training-demand emulation on hardware (8 and 40 emulated jobs: real input pipeline, paced consumer, no GPU); simulation only as the reference for decisions | **preliminary validation, pilot, and the fixes and checks for the comparison done (2026-11-24, evening); the comparison itself (five runs of 20 minutes) has not been run.** The user approved it on 2026-11-24 (at most 9.8 TB of BeeGFS reads, 5 to 6.5 expected; 20 nodes for about 2 h 15 min); it is queued and starts by itself when disk counters run on at least three storage servers (no server had a free CPU on 2026-11-24; expected 2026-11-25) | The prototype is correct at full scale: decisions equal to the simulator on 403,200 accesses of 40 jobs over the 524,288-file catalog and on the pilot's logs; 40,960 requests through the full store compared byte for byte, none differs; two-epoch lookahead takes the same decisions as one-epoch lookahead on this workload. The miss path through one machine carries 12.1 GB/s on data in the storage servers' memory and equals direct reads on cold and mixed data with 320 streams. 40 emulated jobs on cold storage stall directly from BeeGFS: 47% of their rate, 53% waiting. **Negative or limiting:** in its first three minutes the cache with known order and prefetching, empty at the start, delivered 11% fewer samples than direct BeeGFS and needed 40 s to start; as one BeeGFS client the server received 0.78 GB/s of a saturated storage where 20 direct nodes received 0.92; 65% of the prefetches were late at the storage limit; the known-order policy stalled the manager for 4.6 to 4.8 s every 131,072 requests at this scale (measured without a server; since the evening of 2026-11-24 the pass is computed with arrays in 0.07 to 0.09 s with every decision and key unchanged against the simulator on 806,400 accesses); the prefetcher of the morning's experiment ran far ahead of its window with jobs of several read streams (corrected); consecutive configurations with identical sequences are not independent, because the storage servers still hold the earlier run's files; no disk counters could be read, so nothing is known about disk reads. No statement yet on known order against static pinning or on the steady state. **Second part (evening):** the cache client now works on nodes with several RDMA devices; 40 jobs start and run through the comparison's scripts with decisions equal to the simulator (two runs of 90 s: 45% to 47% of the rate, 53% to 54% waiting, as direct BeeGFS in the pilot); other users' reads can now be measured per user. Expected from simulation, not measured: in a 20-minute run known order is still building up its reuse in the second half (hit share 1 − exp(−n/N) until the jobs have made N requests in all), so that half separates it from static pinning but is not a steady state. |
| 2026-11-24 | `2026-11-24-two-epoch-lookahead-prefetch` | Can jobs announce their order two epochs ahead without changing it, and does asynchronous prefetching, coordinated with the unchanged known-order replacement, reduce data waiting? | implementation (prefetch path in the data plane, prefetcher in the manager, lookahead mode `epoch2`); simulation (trace-driven scheduling analysis with a storage model fitted to earlier measurements); real hardware at small scale (four CosmoFlow training jobs on four GPU nodes, cache store in CXL memory, pools of 1,024 to 2,048 cold files) | done at small scale (2026-11-24); no large multi-job run | Two-epoch announcement leaves the order untouched (no mismatch in test clients and in training). Prefetching removed the waiting of one-stream training jobs on cold files: 39.5% directly, 18.7% through the cache without prefetching, 0.5% with it, 99.9% of the prefetches complete in time. **Negative or limiting:** a direct job with eight read streams also waits 0.5%; prefetching read 8% to 11% more from BeeGFS than replacement alone on a shared pool; two-epoch lookahead changed no waiting (0.1 to 2.9 points of hit rate in simulation, 2% of BeeGFS reads on hardware); on a small shared pool no cache configuration differs from direct BeeGFS after the first epoch, because the storage servers' memory serves the pool. Simulation: under a storage-bandwidth deficit prefetching changes nothing (24.4% waiting with and without). One model expectation was refuted on hardware and the model corrected. |
| 2026-11-18 | `2026-11-18-large-working-set-reuse` | Why did reused data stay fast for 20 jobs although one thread read it at cold latency, and can a workload on this cluster have cross-job reuse and a storage stall at once, so that the cache could shorten training? | real hardware: storage tests with one thread and with 160 streams (20 client nodes), disk and memory counters read on three or four of the seven storage servers, and one run of 20, then 26 emulated training jobs (real input pipeline, paced consumer, no GPU) on the full dataset from direct BeeGFS; plus a trace simulation of full-dataset workloads with the four policies | done in part (2026-11-18): storage residency and workload analysis complete; the cache comparison was not run | The storage is 14 single hard disks. The slowest server sets a cold ceiling of 0.66 to 0.86 GB/s, and many readers get that ceiling divided by the share of bytes that comes from disk (measured at shares of 1, 0.5, 0.33). One thread times a file by its slowest chunk and says nothing about that. **Negative for the cache at this scale:** 20 jobs sharing the full 1.52 TB set did not wait for storage (0.8% waiting, as from memory), because the storage servers' memory served 40% of the bytes; 26 jobs waited 3%. No cache run was made. Simulation: known order serves 49% of the bytes from a 256 GiB cache against 15% for static pinning, but with the servers' memory behind the cache the disks' load is no lower than with static pinning. |
| 2026-11-17 | `2026-11-17-cxl-cache-integration` | Can a minimal shared cache with its store in CXL memory serve CosmoFlow training jobs correctly, with the simulator's policies, and does it shorten training where shared storage limits 20 concurrent jobs? | implementation and real hardware: cache server on c28 (store in CXL memory, `/dev/dax1.0`, or in DRAM), test clients and training on up to 20 GPU nodes (RTX 4060 Ti; c39 to c43, c73, c78, c79, c37, c60 to c70); simulation only as the reference the server's decisions are checked against | done in reduced form (2026-11-17); the full-dataset evaluation with 256 and 512 GiB caches was not run | The cache works: 877,280 objects equal to their files, decisions equal to the simulator on 10.7 million trace accesses and on the logs of 47 server runs, 12.3 to 12.4 GB/s of hits from CXL memory and from DRAM alike, training tensors unchanged. With 20 real jobs on a shared pool the known-order policy served 50.6% and 68.9% of the bytes at 18% and 36% capacity (progress-aware 26.0% and 46.4%, LRU 17.2% and 34.7%, static pinning 17.7% and 35.5%). 20 jobs on never-read data: direct BeeGFS 274.5 samples/s (17.3% waiting), through the cache with half hits 331.4, all hits 331.3, all misses 260.2. **Negative:** direct BeeGFS ran at the same full rate wherever the data had been read before (twice 10 and 50 minutes earlier, or once 95 minutes earlier; the last although a single-thread probe read the files at cold latency), and on the shared pool, which the storage servers held in memory, no policy changed training speed. No gain of the cache over direct BeeGFS on reused data was measured. |
| 2026-11-17 | `2026-11-17-multi-gpu-io-saturation` | At how many concurrent GPU jobs does shared BeeGFS limit real CosmoFlow training when every job has a parallel, asynchronous loader, and which multi-job configuration should the cache experiment use? | real hardware: training on up to 20 GPU nodes (RTX 4060 Ti; c39 to c44, c73 to c79, c37, c60 to c62, c66, c56, c20), one job per node, each job on its own cold files of the full training set, exactly 2 or 8 files read at a time; plus a trace simulation | done (2026-11-17) | The storage limit was reached. With two read streams per job: no waiting at 1, 7, and 9 jobs; 12 jobs waited 17% in the first run of the day and 0.3% in a repetition; 15 jobs wait 13% (83% of linear aggregate throughput), 20 jobs 25% (237 of 323 samples/s, 73%). With eight read streams per job: 15 jobs do not wait, 20 jobs wait 20% (81% of linear), with requests queuing at the storage servers; the jobs get at most 0.76 GB/s of first reads (0.80 GB/s leave the servers) against a demand of 0.95 GB/s, so the limit for a well-configured loader lies at about 16 to 17 jobs of this GPU class, as estimated before. Re-read data and memory-resident input give the full rate (16.2 samples/s per job, 0.3% waiting) at every job count: 1.24 times faster in aggregate than first reads at 20 jobs with eight streams, 1.38 times with two. Limits and negatives: single runs of under a minute per configuration; the one repeated configuration did not reproduce; the planned 8-job and 10-job runs ran with 7 and 9 jobs; three nodes ran at half CPU clock and wait for storage even alone; every first read is cold by construction, which a shared dataset read by 20 jobs is not entirely. Simulation on a new real twenty-job trace (shared subset, same start): known order 59.5% against 19.6% static, 27.5% LRU, and 60.0% offline at 20% capacity. No cache and no CXL memory involved. |
| 2026-11-16 | `2026-11-16-loader-gpu-scaling` | How do the number of concurrent readers and the number of concurrent jobs change training throughput and waiting for storage, and which configurations are candidates for the cache experiment? | real hardware: training on c28 (one GPU) and on eight identical GPU nodes (c60 to c62, c68 to c72), cold files of the full training set; plus a trace simulation | done (2026-11-16) | A job waits for cold storage only with exactly one read stream: 12.5 samples/s and 26% waiting on c28 against 16.86 from memory (1.35 times); with 2, 4, 8, or 16 streams it runs at 16.85 from cold data. Eight concurrent jobs: no waiting with the baseline reader or with two streams (135 samples/s and 0.39 GB/s in total); with one stream per job 9.9 samples/s and 41.5% waiting each, against 11.2 and 34% for one such job, and 16.84 from memory (1.70 times). Negative: a second read stream gives the same gain as memory without any cache, and eight jobs of this GPU class reach only half of the shared first-read supply, so no configuration was found in which a well-configured loader waits. Finding on method: tf.data's interleave reads ahead up to three files per cycle slot, so its cycle length is not a reader count; an exact-reader pipeline was added. Simulation on a new real eight-job trace (equal speeds, same start): known order 57.3% against 19.1% static and 58.6% offline at 20% capacity, Quiver-inspired replay 88.3%. No cache and no CXL memory involved. |
| 2026-11-16 | `2026-11-16-workload-io-validation` | Which workload gives a shared CXL cache a real opportunity, and is CosmoFlow training limited by storage reads, by CPU work in the input pipeline, or by the GPU? | real hardware: training and input-pipeline measurements on c28, a two-job run on c24 and c38, storage probes from c28 and c73 to c76; plus a trace simulation and analytical estimates for other workloads | done (2026-11-16) | Full CosmoFlow (measured: 524,288 files, 1,519.75 GB) with several concurrent jobs stays the primary workload; MLPerf Storage 3D U-Net is the alternative. Negative for one job: with a parallel reader, training on an RTX 4060 Ti runs at 16.86 samples/s from first-read BeeGFS, re-read BeeGFS, and host memory alike (0.4% waiting), so memory-resident data gains nothing; only the benchmark's sequential reader waits for storage (60% of the time, memory 2.16 times faster), and parallel reading removes that without a cache. The input pipeline costs about 73 ms of CPU per sample and caps a 16-core node at 209 samples/s. First-read supply is one limit shared by all clients, 0.74 GB/s at 32 streams (about 255 samples/s), so storage would bind only at about 15 such jobs or four A100-class GPUs (analytical). Once-read data left the storage servers' memory within an hour that afternoon, and the dataset is 2.2 times their memory, so full-dataset epochs are cold. Simulation on a new real two-job trace with logged job identity and unequal speeds: the policy order holds with a smaller margin (known order 30.9% against 18.0% static and 34.3% offline at 20% capacity), and the Quiver-inspired replay loses its lead. No cache and no CXL memory involved. Correction: the "parallel reader" of this experiment is tf.data's interleave with cycle length 8, which reads up to 24 files at once (see `2026-11-16-loader-gpu-scaling`). |
