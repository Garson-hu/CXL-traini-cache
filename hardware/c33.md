# c33 — Machine Used for Earlier CosmoFlow Training Experiments

c33 was used for CosmoFlow training experiments that predate this repository.
It has not been logged into or used by this project.

c33 results must never be merged with [c28](c28.md) CXL results as if they came
from one integrated system. c33 has an A100 GPU and no CXL memory known to this
project; c28 has CXL memory and a much smaller GPU.

This file separates:

1. **Provided context** — from the project brief.
2. **Verified current information** — read from the scheduler on 2026-11-11, without logging in.
3. **Historical records** — from the earlier repository, with their source. Not reproduced here.

### Reuse distances (from the project brief)

Between consecutive accesses to the same file, in intervening file reads:

### Conclusions drawn by the earlier study (theirs, not verified here)

- The full run was compute-bound in epochs 1-2 at about 0.217 GB/s of files.
- One BeeGFS stream (0.064 GB/s) is about 3.4 times too slow for that trainer;
  four or more streams are enough.
- With the sequential reader the benchmark was I/O-bound at 5.4 samples/s.
- In a trace-driven simulation, prefetching hid storage latency whenever the
  storage bandwidth exceeded the demand.

## 4. Caveats

- The earlier report attributes the faster epochs 1-2 to c33's page cache. On
  c28, BeeGFS reads leave nothing in the client page cache and re-reads are
  still fast ([c28.md](c28.md), section 3.1), which points to caching on the
  storage servers. c33's client configuration was not checked, so the cause on
  c33 remains open.
- The c33 trainer used batch size 4 on an 80 GB GPU. c28's GPU ran the model
  only at batch size 1 and 2 in a small check.
- These numbers are not evidence that CXL caching accelerates training. No CXL
  memory was involved.
- Before citing any value in a report or paper, re-read the original files on
  the branch named above.
