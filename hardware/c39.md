# c39 and c44 — Client Nodes Used for Remote Data-Path Measurements (with notes on c24, c38, and the storage servers)

Experiment `2026-11-12-remote-cxl-data-path` drives the cache server on
[c28](c28.md) and reads BeeGFS directly from these nodes: c39 on 2026-11-12,
c44 on 2026-11-15 (c39 was then allocated to another user). They stand in for
[c33](c33.md), which was fully allocated to another user's job on both days.
Both are in the same Slurm partition (`rome`) and run the same kernel as c33.
Neither has CXL memory.

**c44** was inspected on 2026-11-15 inside Slurm job 341556: AMD EPYC 7302P
(16 cores, 32 threads), 125 GiB, kernel 5.19.9, `mlx5_0` 100 Gb/s (2X HDR),
BeeGFS client settings as below, idle. It matches c39 in every item checked.
All paths compared in the experiment's report were measured from c44.
Sections 1 and 2 describe c39.

Results measured with one of these nodes as the client and c28 as the server
are results of that pair. They must not be merged with c33 training results as if they came
from one system ([CLAUDE.md](../CLAUDE.md), research integrity).

users' jobs run on them and compete with the file cache for memory.

|---|---|---|---|---|---|
| 2026-11-12 | c11, c14 | 93 GiB each | 50 to 52 GiB | not recorded | not recorded |
| 2026-11-16 13:32 | c14 | 93.1 GiB | 88.7 GiB | 72.9 / 12.9 GiB | 0.7 GiB |
| 2026-11-16 13:32 | c15 | 93.1 GiB | 89.8 GiB | 70.9 / 15.8 GiB | 0.5 GiB |

Source: `/proc/meminfo` in one-task jobs of under a minute. On 2026-11-16
both servers were reading 10 to 16 MB/s from their disks and reclaiming 3 to

The other servers were allocated to other users and were not entered.

can be in the storage servers' memory at once.

Each server holds two storage targets of 9,240 GiB (14 targets; 13% to 24%
free on 2026-11-17, `beegfs-ctl --listtargets --spaceinfo`). The CosmoFlow
training directory is striped over 4 targets with 512 KiB chunks
(`beegfs-ctl --getentryinfo`), so one 2.9 MB file is read from four targets.
`beegfs-ctl --serverstats --nodetype=storage` can be read without
privileges: bytes read and written per second, requests, queue length, and
busy worker threads, per server or summed, for all clients of the file
system.

`beegfs-ctl --userstats --nodetype=storage --interval=0` can also be read
without privileges (found on 2026-11-24, 20:55): per user the bytes read
from and written to the storage servers since they started, printed with
six significant digits. Sampled every 10 s it separates this project's
reads from the sum of all other users' reads; scripts of this project
store only that sum and name no user. With standard input closed the tool
prints the totals once and exits, so it is called once per sample.

The storage servers export no metrics: ports 9100, 8649, and 9273 are
closed on c12 and c14 (2026-11-24, 20:50). Their disk counters
(`/proc/diskstats`) can only be read from a Slurm job on the server
itself. **Slurm allocates whole nodes here** (`SelectType = select/linear`,
partition `all` with `OverSubscribe=NO`; seen on 2026-11-24, 22:08: a job
that asked for one task and one CPU on c11 was given all 16 CPUs). A
monitor can therefore run only on a storage server that no other job
holds, and while it runs it keeps that server from every other job.
Earlier notes of this project that say a monitor needs "a free CPU" mean
a free node. On the evening of 2026-11-24 all seven servers were held by
other users' jobs until 2026-11-25 (c17 until 05:45, c16 until 13:53, c12
to c15 until 14:00); c11 became free at 22:02, where the new monitor
script (`disk_monitor.sh` of experiment
`2026-11-24-large-scale-cache-evaluation`) then ran for eight minutes and
found the data disks by their mount points (`sdc` on `/mnt/data`, `sdd`
on `/mnt/data2`, 9.1 TB each; system disk `sda`, SSD `sdb`).

### RDMA devices and Mercury on the client nodes (2026-11-24, 20:55)

Read-only probe on c51, c58, and c50 (`/sys/class/infiniband`, `ip`,
`fi_info -p "verbs;ofi_rxm"`, and Mercury initialisation in the cache
client library with different address strings):

| Node | RDMA devices | `ofi+verbs;ofi_rxm://<ib0 address>` | with `FI_VERBS_IFACE=ib0` | `ofi+verbs;ofi_rxm://mlx5_0/<ib0 address>` |
|---|---|---|---|---|
| c51 | `bnxt_re0` (eth0), `bnxt_re1` (second Ethernet port), `mlx5_0` (ib0), all active | **fails** | works | works |
| c58 | the same three | works | works | works |
| c50 | `mlx5_0` only | works | works | works |

libfabric offers the `verbs;ofi_rxm` provider on all three devices of c51
and c58 under one fabric name. Why the address alone is enough on c58 and
not on c51 was not examined (the second Ethernet port has another
interface name on the two nodes). Since 2026-11-24 the cache client names
the RDMA device of `ib0` in its address (third column); clients on c51 and
c52 then connected to a server on c28 and received 128 verified objects
each.
