# c28 — Development and CXL Machine

c28 is the machine this project is developed on and the only machine in the
project with CXL memory devices.

Results measured on c28 must never be merged with results from
[c33](c33.md) as if they came from one integrated system. See
[CLAUDE.md](../CLAUDE.md), "Research integrity".

This file separates four kinds of information:

1. **Provided context** — stated in the project brief, not independently checked.
2. **Verified by read-only inspection** — observed on the machine, with date and command.
3. **Lightweight validations** — small checks run for this project. Not benchmarks.
4. **Historical measurements** — taken on c28 by earlier work, not reproduced here.

No performance experiment of this project has run on c28 yet.

Audit history: first inspection 2026-11-11 about 21:20, second and more
detailed inspection 2026-11-11 about 23:05. Values can change; re-check before
relying on them in an experiment.

## 1. Provided context (not independently verified)

- CPU: AMD EPYC 9745.
- Large DDR5 DRAM capacity.
- Multiple Micron CZ120 CXL memory devices.
- GPU: NVIDIA RTX 4060 Ti, 8 GB.

### CXL windows and DAX devices

| DAX device | Size | CXL window (root decoder) | Interleave at root | Mode |
|---|---|---|---|---|
| `dax0.0` | 260,382,392,320 B (242.5 GiB) | Window 0 (`decoder0.0`) | 2 ways, granularity 256 | devdax |
| `dax1.0` | 289,373,421,568 B (269.5 GiB) | Window 1 (`decoder0.1`) | 2 ways, granularity 256 | devdax |
| `dax2.0` | 549,755,813,888 B (512 GiB) | Window 2 (`decoder0.2`) | 1 way (one target) | devdax |

- Total 1024 GiB, equal to 4 x 256 GiB. All three: `target_node` 1, align 2 MiB,
  driver `device_dax`, backed by firmware `hmem` ranges (`/platform/hmem.N`).
- The window-to-device mapping follows from matching sizes and from the nesting
  shown in `/proc/iomem` ("CXL Window N" / "Soft Reserved" / `daxN.0`).
- Sources: `daxctl list -DRMi`, `cxl list -D -d root`, `/sys/bus/dax/devices`,
  `/proc/iomem`.

## 3. Lightweight validations (2026-11-11, not benchmarks)

### 3.1 Do BeeGFS reads populate the client page cache?

16 files (46,251,814 bytes) from the full dataset's `validation/` directory,
read sequentially with `cat`, page-cache residency read with `fincore`.

| Step | Result |
|---|---|
| Residency before reading | 0 bytes |
| First read | 1.61 s (28.8 MB/s) |
| Residency after reading | 0 bytes |
| Second read | 0.053 s (874 MB/s) |
| Third read | 0.047 s (978 MB/s) |

Reading: BeeGFS file data is not kept in the Linux page cache on c28, which is
consistent with `tuneFileCacheType = buffered`. Repeated reads were still about
30 times faster. That is consistent with caching on the storage servers, which
this project can neither inspect nor clear. This is one sample of 16 files.

### 3.2 Does the CosmoFlow model fit on the GPU?

Model built from the existing benchmark configuration (8,907,556 parameters,
input 128x128x128x4, float32), six training steps per batch size on synthetic
tensors, TensorFlow 2.14.0 from `hvac_tf`. No dataset I/O, nothing written.

| Batch size | Result | Peak GPU memory | Median step time (5 steps) |
|---|---|---|---|
| 1 | ran | 5.49 GiB (includes cuDNN start-up search) | 0.089 s |
| 2 | ran | 3.02 GiB | 0.154 s |
| 4 | `ResourceExhaustedError` | — | — |

Reading: TensorFlow sees the GPU and the model trains at batch size 1 and 2.
Batch size 4 did not fit in this check. The step times correspond to roughly
11-13 samples/s. That is an indication from five steps on synthetic data, not
a measurement, and it excludes the input pipeline.
