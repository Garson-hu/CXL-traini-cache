# c28 — Development and CXL Machine

c28 is the machine this project is developed on and the only machine in the
project with CXL memory devices.

Results measured on c28 must never be merged with results from
[c33](c33.md) as if they came from one integrated system. See
[CLAUDE.md](../CLAUDE.md), "Research integrity".

This file separates four kinds of information:

1. **Provided context** — stated in the project brief, not independently checked.
2. **Verified by read-only inspection** — observed on the machine, with date and command.
3. **Lightweight validations** — small checks run for this project. Not benchmarks.
4. **Historical measurements** — taken on c28 by earlier work, not reproduced here.

Measurements of this project on c28 are in section 6.

Audit history: first inspection 2026-11-11 about 21:20, second and more
detailed inspection 2026-11-11 about 23:05. Values can change; re-check before
relying on them in an experiment.

## 1. Provided context (not independently verified)

- Large DDR5 DRAM capacity.
- Multiple Micron CZ120 CXL memory devices.

16 files (46,251,814 bytes) from the full dataset's `validation/` directory,
read sequentially with `cat`, page-cache residency read with `fincore`.

| Step | Result |
|---|---|
| Residency before reading | 0 bytes |
| First read | 1.61 s (28.8 MB/s) |
| Residency after reading | 0 bytes |
| Second read | 0.053 s (874 MB/s) |

Reading: BeeGFS file data is not kept in the Linux page cache on c28, which is

Reading: TensorFlow sees the GPU and the model trains at batch size 1 and 2.

## 6. Measurements of this project

Experiment `2026-11-12-remote-cxl-data-path`, c28 part on 2026-11-15, with
the first 16 GiB of `/dev/dax1.0` and of `/dev/dax0.0` (bytes
[0, 17,179,869,184) of each) as agreed by the user on 2026-11-12. The other
experiment had left the machine; no process mapped a DAX device.
**[Observed]**, object-sized `memcpy` (2.9 MB) between the store and private
DRAM buffers, 2 MiB mappings, median of three 4-second runs:

| Threads | DRAM read | CXL read (`dax1.0`) | DRAM write | CXL write (`dax1.0`) |
|---|---|---|---|---|
| 1 | 36 GB/s | 24 GB/s | 36 GB/s | 34 GB/s |
| 4 | 132 GB/s | 52 GB/s | 73 GB/s | 47 GB/s |
| 16 | 107 GB/s | 52 GB/s | 69 GB/s | 48 GB/s |

- `dax0.0` gave the same: about 51 GB/s read and 45 GB/s write.
- Eight readers and eight writers at once on CXL: 38 + 31 GB/s, more than
  either alone.
- **Device writes into CXL memory are slow.** When the InfiniBand NIC writes
  into a devdax mapping (RDMA into the registered CXL range), the rate is
  capped at 4.24 GB/s on both devices, against 12.35 GB/s into DRAM, and
  concurrent NIC reads of CXL memory drop from 12.3 to 0.77 GB/s. NIC reads
  of CXL memory alone run at the link limit. The cause is not identified.
- These are copy rates of one byte range per device, not a full
  characterization of the CXL devices.

### Cache server (2026-11-17)

Experiment `2026-11-17-cxl-cache-integration`
([docs/experiments/INDEX.md](../docs/experiments/INDEX.md)) ran the cache
prototype ([system/](../system/README.md)) on c28, CPUs 0 to 47, with its
store in `/dev/dax1.0`. The user agreed on 2026-11-17 to the whole device
for that experiment; used were bytes [0, 53,217,329,152) and
[68,719,476,736, 70,850,183,168). `/dev/dax0.0` and `/dev/dax2.0` were not
touched. Before every start no other process mapped the device.

**[Observed]**

| Item | Value |
|---|---|
| Hits served over Mercury, store in CXL memory, 1 / 2 / 4 / 8 client nodes | 12.27 / 12.31 / 12.37 / 12.38 GB/s (4,231 to 4,268 objects of 2.9 MB per second) |
| The same with the store in DRAM | 12.26 / 12.31 / 12.39 / 12.39 GB/s |
| Server CPU while serving hits | 7 to 12 ms per GB, about 0.1 cores at the link rate |
| Control plane (Python) per request | 7 to 9 µs for hits with the static policy |
| Registration of a 53 GB devdax range for RDMA, read-only | 0.56 s |
| 20 training jobs, all requests misses and admitted (44.5 GB read from BeeGFS, sent, and copied into CXL memory in about a minute) | 23 s of CPU, no error |

The CXL store equals the DRAM store in every hit measurement, as the raw
data path did on 2026-11-15. As the only BeeGFS client for the misses of 20
jobs, c28 read 0.82 GB/s of cold files with 192 worker threads; the storage
servers showed no queue then (0.2 requests on average, against 46 when 20
nodes read directly), which fits the limit of 12 connections per storage
server on a client (`connMaxInternodeNum`).
